# FEL DRONE — I18N — Français · English · العربية (V11)

> Shipped trilingual interface: three typed dictionaries, one tiny React
> context, **no framework migration and no i18n dependency**. French remains
> the default and the reference language.

## What the visitor gets

| Language | Direction | Selector | Coverage |
| -------- | --------- | -------- | -------- |
| Français | LTR | FR | Reference language — the V10 copy, unchanged |
| English  | LTR | EN | Full customer-facing translation (B2B, factual) |
| العربية  | **RTL** | AR | Full customer-facing translation, Arabic script |

The selector sits in the header rail (desktop) and in the mobile sheet, always
reachable. It is a state switch, **not a route**: the site is one bundle with
hash navigation, so no URL changes and every deep link (`#services`, `#contact`,
`#mentions-legales`, …) keeps working in all three languages — section ids are
language-independent.

## Architecture

```
src/i18n/types.ts        Dictionary contract + Locale/Direction types
src/i18n/index.tsx       I18nProvider · useI18n() · useDict() · detectLocale()
src/data/company.ts      Language-independent identity (legal name, RC, phone…)
src/data/content.fr.ts   French dictionary  (reference)
src/data/content.en.ts   English dictionary
src/data/content.ar.ts   Arabic dictionary
```

- `Dictionary` is an exact type: `npm run typecheck` fails if a language is
  missing a field, so a half-translated interface cannot compile.
- `src/data/company.ts` is the single source of the Registre de Commerce
  number, the phone, the e-mail and the proper names; each dictionary carries
  only what must be *read* in that language (labels, copy, place names,
  image alternative text).
- `detectLocale()` order: stored preference → browser language → `fr`.
  The choice is written to `localStorage` under `fel-drone:locale`.
- The provider applies `document.documentElement.lang`, `…dir`,
  `data-locale` and `document.title` in a layout effect — the first paint is
  already in the right language and direction (no LTR flash before Arabic).

## RTL rules (Arabic)

- Direction comes from `dir="rtl"` on the shell — not from a flipped
  stylesheet. Components use logical utilities (`ps-*`, `pe-*`, `ms-*`,
  `me-*`, `start-*`, `end-*`, `text-start`, `border-s`), so the layout mirrors
  by itself and stays correct in LTR.
- Directional icons rotate (`rtl:rotate-180` on the arrow glyphs); the brand
  lockup does **not** — an `<svg>` keeps `direction: ltr` because the mark and
  the two-word lockup are Latin and would otherwise reorder.
- Latin locks inside Arabic text are isolated: the RC number (`36/00-0683602B26`),
  phone numbers, Plus Codes, e-mail and form counters use `dir="ltr"`, `<bdi>`
  or `unicode-bidi: isolate` (see `src/index.css`).
- Arabic typography: `IBM Plex Sans Arabic` is loaded next to `IBM Plex Sans`
  (same superfamily, same weights 400–700), `letter-spacing` is reset inside
  Arabic text (tracking breaks Arabic joining), and headings get a slightly
  larger line height.

## Content rules

1. **Never change facts while translating.** Prices policy, caveats
   (“À compléter”, “Exemple de démonstration — non issu d'une mission client”,
   “sur devis”), certifications, team, contacts and legal identifiers are the
   same statement in all three languages.
2. **No invented copy.** English and Arabic say exactly what the French
   reference says — no added promise, no added capability.
3. **“À compléter” is translated, not dropped**: EN “To be completed”,
   AR “قيد الاستكمال”.
4. **Canonical API values stay French.** `services.list[].apiValue` and
   `contact.form.options[].value` are the identifiers sent to
   `POST /api/quote` in every language — the API contract, its validation,
   honeypot and rate limiting are untouched by the locale.
5. **Proper names stay as they are**: FEL DRONE, the fellows' names, NDVI,
   MNT/DTM, RGB, SARL, WhatsApp, Plus Code, wilaya names as written on
   Algerian documents.

## Validation

```bash
npm run typecheck   # dictionary contract is exact
npm run check:i18n  # completeness, placeholders, French leakage, RTL, RC number
npm run brand:check # brand assets untouched by the language work
npm run test:api    # the API contract still holds
npm run build       # FR + EN + AR ship in one bundle
```

`scripts/check-i18n.mjs` verifies, among others: no empty string, no
“Translation here / À traduire / TODO” marker, no French UI phrase inside the
English or Arabic dictionary, Arabic really written in Arabic script, the three
languages declaring the same structure (9 nav links, 7 services with the same
canonical values, 8 method steps, 6 FAQ entries, 8 form options, 4 sectors,
4 demonstration items, 3 equipment groups, 3 team members, alternative text for
every photograph), and no visible French string hard-coded inside a component.

## What NOT to do

- Do not add an i18n library, a router or a framework migration for languages.
- Do not create `/fr`, `/en`, `/ar` routes: the site is a single-page bundle
  with hash navigation, and the current deployment (Pages branch source,
  Vercel root) must keep serving one entry.
- Do not translate the canonical API service values.
- Do not translate the Registre de Commerce number, the phone number, the
  e-mail address or the proper names.
- Do not silently fall back to French inside an English or Arabic screen.
